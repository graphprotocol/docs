---
title: Use Immutable Entities and Bytes as IDs
---

Two schema changes [significantly improve](https://thegraph.com/blog/two-simple-subgraph-performance-improvements/) indexing speed, query performance, and storage: marking entities that never change as immutable, and using `Bytes` for IDs.

## Immutable Entities

To make an entity immutable, add `(immutable: true)` to it:

```graphql
type Transfer @entity(immutable: true) {
  id: Bytes!
  from: Bytes!
  to: Bytes!
  value: BigInt!
}
```

When the `Transfer` entity is immutable, Graph Node processes it more efficiently, which speeds up indexing and queries.

An immutable entity never changes after it is created. The best candidates are entities that log onchain event data directly, such as a `Transfer` event stored as a `Transfer` entity.

### Under the Hood

Mutable entities have a 'block range' indicating their validity. Updating these entities requires Graph Node to adjust the block range of previous versions, increasing database workload. Queries also need filtering to find only live entities. Immutable entities are faster because they are all live and since they won't change, no checks or updates are required while writing, and no filtering is required during queries.

### When Not to Use Immutable Entities

If an entity has a field that changes over time, such as `status`, do not make it immutable: a write to an immutable entity causes an indexing error. Otherwise, use immutable entities whenever possible.

## Bytes as IDs

Every entity requires an ID. In the previous example, the ID is already of type `Bytes`.

```graphql
type Transfer @entity(immutable: true) {
  id: Bytes!
  from: Bytes!
  to: Bytes!
  value: BigInt!
}
```

Other ID types, such as `String` and `Int8`, are possible, but use `Bytes` for all IDs where you can. Character strings take twice as much space as byte strings to store binary data, and comparing UTF-8 strings must take the locale into account, which costs much more than the bytewise comparison used for `Bytes`.

### Reasons to Not Use Bytes as IDs

1. Entity IDs must be human-readable, such as auto-incremented numbers or readable strings.
2. The Subgraph's data must integrate with another data model that does not use `Bytes` IDs.
3. Indexing and query performance are not a concern for this entity.

### Concatenating With Bytes as IDs

It is a common practice in many Subgraphs to use string concatenation to combine two properties of an event into a single ID, such as using `event.transaction.hash.toHex() + "-" + event.logIndex.toString()`. Because this returns a string, it significantly slows indexing and queries.

Instead, use the `concatI32()` method to concatenate event properties. The result is a `Bytes` ID that is much faster to store and compare.

```typescript
export function handleTransfer(event: TransferEvent): void {
  let entity = new Transfer(event.transaction.hash.concatI32(event.logIndex.toI32()))
  entity.from = event.params.from
  entity.to = event.params.to
  entity.value = event.params.value

  entity.blockNumber = event.block.number
  entity.blockTimestamp = event.block.timestamp
  entity.transactionHash = event.transaction.hash

  entity.save()
}
```

### Sorting With Bytes as IDs

Sorting by a `Bytes` ID does not give numeric order, as this example query and response show.

Query:

```graphql
{
  transfers(first: 3, orderBy: id) {
    id
    from
    to
    value
  }
}
```

Query response:

```json
{
  "data": {
    "transfers": [
      {
        "id": "0x00010000",
        "from": "0xabcd...",
        "to": "0x1234...",
        "value": "256"
      },
      {
        "id": "0x00020000",
        "from": "0xefgh...",
        "to": "0x5678...",
        "value": "512"
      },
      {
        "id": "0x01000000",
        "from": "0xijkl...",
        "to": "0x9abc...",
        "value": "1"
      }
    ]
  }
}
```

The IDs are returned and sorted as hex.

To sort by a number, add a `BigInt` field to the entity:

```graphql
type Transfer @entity {
  id: Bytes!
  from: Bytes! # address
  to: Bytes! # address
  value: BigInt! # unit256
  tokenId: BigInt! # uint256
}
```

Then order by that field:

Query:

```graphql
{
  transfers(first: 3, orderBy: tokenId) {
    id
    tokenId
  }
}
```

Query Response:

```json
{
  "data": {
    "transfers": [
      {
        "id": "0x…",
        "tokenId": "1"
      },
      {
        "id": "0x…",
        "tokenId": "2"
      },
      {
        "id": "0x…",
        "tokenId": "3"
      }
    ]
  }
}
```

## Results

In a controlled test, using immutable entities and `Bytes` IDs together cut time per block by 28%, sync time by 26%, and storage by 48%. See [Benchmarks and Evidence](/subgraphs/best-practices/overview/#benchmarks-and-evidence) for the full comparison.
